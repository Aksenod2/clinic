## 3. Требования к Системе в целом

### 3.1. Технологический стек (фиксируется как есть в прототипе)

| Слой | Технология |
|------|-----------|
| Frontend / Backend | Next.js 14 (App Router), React 18, TypeScript |
| Вёрстка / UI | TailwindCSS, shadcn/ui (Radix UI), lucide-react |
| База данных | PostgreSQL |
| ORM | Prisma 5 |
| Аутентификация | NextAuth.js (credentials, bcrypt) |
| Валидация | Zod, react-hook-form |
| Хостинг | `‹Vercel / VPS — согласовать, см. раздел 9›` |

Смена стека возможна только по письменному согласованию сторон.

### 3.2. Требования к совместимости и адаптивности

- Адаптивная вёрстка (mobile-first): телефоны, планшеты, десктоп; брейкпоинты ≥ 360 px.
- Поддержка двух последних мажорных версий Chrome, Firefox, Safari, Edge.
- Корректная работа на iOS Safari и Android Chrome.

### 3.3. Требования к производительности

- TTFB ключевых страниц ≤ 600 мс при штатной нагрузке.
- Изображения отдаются в современных форматах (WebP/AVIF), с lazy-load и адаптивными размерами (`next/image`).
- Кэширование статики и ISR/SSG для контентных страниц где применимо.

### 3.4. Требования к надёжности и эксплуатации

- Резервное копирование БД не реже 1 раза в сутки (на стороне хостинга/Исполнителя — согласовать).
- Логирование ошибок (server-side) и базовый мониторинг доступности.
- Развёртывание через CI/CD (например, GitHub Actions) с возможностью отката.

### 3.5. Требования к безопасности и защите ПДн (критично — медицина)

> Тематика чувствительная (репродуктивное здоровье, анонимность пациентов). Требования обязательны.

- Весь трафик только по HTTPS (TLS), редирект с http → https.
- Раздел `/admin/*` закрыт авторизацией (middleware), пароли хранятся в виде bcrypt-хэшей.
- Пароль администратора по умолчанию из прототипа (`admin123`) **подлежит смене** до запуска; учётка-сидер отключается.
- Все формы со сбором ПДн содержат **обязательный чек-бокс согласия** на обработку ПДн со ссылкой на «Политику конфиденциальности» и «Согласие на обработку ПДн».
- Защита форм от спама/ботов (rate-limit и/или капча — согласовать тип).
- Защита от типовых уязвимостей: XSS, CSRF, SQL-инъекции (через Prisma/параметризацию), валидация всех входных данных (Zod) на сервере.
- Секреты (DB, NEXTAUTH_SECRET и пр.) хранятся только в переменных окружения, не в репозитории.
- Соответствие 152-ФЗ: уведомление о cookies, минимизация хранимых ПДн, ограничение доступа к лидам ролью администратора.

## 6. Функциональные требования

### 6.1. Публичная часть

**6.1.1. Главная**
Блоки-офферы (ведение/диагностика беременности, женское здоровье), лента «Акции и новости» с фильтром «Все / Новости / Акции», блок филиалов (адрес, метро, часы, телефон), быстрый доступ к записи, верхнее мега-меню по направлениям.

**6.1.2. Направление (hub)** `/napravleniya/[slug]`
Описание направления, список связанных услуг, связанные врачи и проблемы, кнопка записи, SEO-блок.

**6.1.3. Услуга (leaf)** `/uslugi/[slug]`
Название, краткое и полное описание, цена (в т.ч. «от»), подготовка к услуге, порядок проведения, в каких филиалах оказывается, врачи, связанные акции, призыв к записи.

**6.1.4. «Что мы лечим»** `/chto-my-lechim/[slug]`
Шаблон: что это / причины / когда к врачу / как диагностируем у нас / какие услуги / какие врачи / в каких филиалах / запись.

**6.1.5. Филиалы** `/kliniki`, `/kliniki/[slug]`
Адрес, метро, часы работы, телефоны, карта, как добраться, врачи и популярные услуги филиала, запись.

**6.1.6. Врачи** `/vrachi`, `/vrachi/[slug]`
Список с фильтрами (специальность, филиал). Профиль: ФИО, специальности, опыт, фото, описание, услуги, филиалы, запись к врачу.

**6.1.7. Акции** `/akcii`, `/akcii/[slug]`
Карточки со старой/новой ценой, срок действия, связанные услуги, лендинг-оффер с формой записи.

**6.1.8. Статьи/блог** `/stati`, `/stati/[slug]`
Список с обложками и анонсами, страница статьи (блочный контент), дата публикации, SEO.

**6.1.9. Онлайн-консультации** `/online` и **Запись** `/zapis`
Многошаговая форма (см. 6.3).

**6.1.10. Глобальные элементы**
Шапка с мега-меню и телефоном, мобильное меню, подвал с реквизитами/лицензиями/юр. ссылками, «хлебные крошки», сквозной CTA записи, кнопка обратной связи.

### 6.2. Админ-панель (`/admin/*`)

- Авторизация (NextAuth) + защита middleware.
- Дашборд: сводка по новым заявкам и ключевым сущностям.
- **CRUD** для: Услуги, Направления, «Что лечим», Клиники, Врачи, Акции, Статьи.
- Управление **заявками (лидами)**: список с фильтрами и статусами (`new / in_progress / done / cancelled`), карточка заявки, смена статуса, комментарий.
- Управление связями many-to-many (врач↔клиника, услуга↔клиника, услуга↔врач, проблема↔услуга и т.д.).
- **Загрузка изображений** (фото врачей, обложки статей) — требуется реализация хранилища (см. 9).
- Управление SEO-полями (title, description, keywords) у всех контентных сущностей.
- Блочный контент (rich-text/блоки) для услуг, направлений, статей, проблем.

### 6.3. Формы и сценарий записи

**Форма записи** (`/zapis`, лендинги акций, страницы услуг/врачей):
1. Тип визита: «в клинике» / «онлайн».
2. Направление/специалист.
3. Филиал.
4. Дата и время (или период дня: утро/день/вечер).
5. Данные пациента (имя, телефон, email — опц., комментарий).
6. Обязательное согласие на обработку ПДн.
7. Отправка → создание лида в БД → уведомление ответственному.

**Прочие формы:** обратная связь, обращение к главному врачу (с возможностью прикрепить файл до 10 МБ — согласовать), отклик на вакансию.

Все формы: серверная валидация (Zod), защита от спама, состояния успех/ошибка, сохранение источника заявки (`source`).

### 6.4. Уведомления и интеграции

- Уведомление о новой заявке: `‹Email / Telegram-бот / оба — согласовать›`.
- `‹Интеграция с CRM/МИС — есть ли требование? согласовать›`.
- Веб-аналитика: Яндекс.Метрика и/или Google Analytics, цели на отправку форм.
- `‹Онлайн-оплата — нужна ли? согласовать›`.

## 8. Требования к дизайну и контенту

### 8.1. Дизайн

- Тон: заботливый, спокойный, экспертный; акцент на конфиденциальность и бережное отношение.
- **Дизайн-макеты разрабатывает Исполнитель** (отдельный этап, см. раздел 10): прототипы → макеты ключевых шаблонов (главная, направление, услуга, врач, филиал, форма записи, статья) → согласование с Заказчиком → вёрстка.
- Единая дизайн-система (компоненты shadcn/ui), доступность (контраст, фокус, alt-тексты), кликабельные/некликабельные состояния различимы.
- Логотип, фирменные цвета, шрифты предоставляет Заказчик (бренд-бук). При отсутствии бренд-бука визуальный стиль согласуется отдельно на этапе дизайна.
- Визуальное направление опирается на **референсы, выбранные Заказчиком** (1–2 из подборки в опроснике, см. блок 6 `docs/voprosy-zakazchiku.md`).

### 8.2. Контент и медицинские требования

- **Первичное наполнение выполняет Исполнитель** путём переноса существующего контента с действующего сайта `mesedclinic.ru`: услуги, направления, цены, профили и фото врачей, статьи/новости, контакты филиалов. Написание новых авторских текстов «с нуля» в объём не входит (см. раздел 12).
- **Дальнейшее наполнение и актуализацию** (новые услуги, статьи, изменение цен, акции) Заказчик ведёт **самостоятельно через админ-панель**.
- Юридический контент (лицензии, политика ПДн, согласия, ОМС, реквизиты) предоставляет **Заказчик** (см. раздел 11).
- Обязательные медицинские дисклеймеры: «Имеются противопоказания, необходима консультация специалиста», информация о лицензиях, реквизиты юр. лица.
- Размещение фото врачей/пациентов — только при наличии согласий. Поскольку контент берётся с публичного сайта Заказчика, ответственность за правомерность его публикации несёт Заказчик.

### 8.3. SEO-требования

- ЧПУ (человекопонятные URL), уникальные title/description, заголовки H1–H3, микроразметка Schema.org (`MedicalClinic`, `Physician`, `Service`, `Article`, `BreadcrumbList`).
- Карта сайта `sitemap.xml`, `robots.txt`, canonical, Open Graph.
- Корректная обработка кириллических slug, отсутствие битых ссылок и 404 в навигации.
- Скорость загрузки и Core Web Vitals (см. 3.3).

- Передача доступов (хостинг, репозиторий, БД, аналитика) Заказчику при сдаче проекта.
